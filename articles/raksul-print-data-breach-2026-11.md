ネット印刷「ラクスル」の、データ入稿（印刷会社に印刷用のデータを送ること）に関わるシステムへの不正アクセスが、2026年11月9日に公表されました。
会員情報の漏えいと違うのは、名刺やはがきの印刷データに載った「ラクスルを使っていない人」の情報も含まれる場合がある点です。
この記事では公式発表から事実を整理し、立場ごとにできることと、入稿する側が手元で使える小さなスクリプトをまとめます。

![](/images/raksul-print-data-breach-2026-11/thumbnail.png)

:::message
**TL;DR**（2026年11月9日の公式発表時点。11月10日朝に同社ニュース一覧を確認した時点で続報なし）
- 11月8日0時20分ごろ発覚。システムの認証情報が不正に取得され、保管データの一部に外部からアクセスできる状態だったと発表されています。件数と原因の詳細は調査中です。
- 対象は入稿された印刷データや請求書・Web郵便などに載った氏名・住所・電話番号・メールアドレスなど。クレジットカード情報・ログインID・パスワードは「漏えいしていないことを確認」したとされています。
- 入稿する側にできるのは、何人分を預けているかを知ること。この記事では、個人情報らしき文字列の出現回数だけを数える Python スクリプトを、ダミーデータで動かした結果と限界つきで載せています。
:::

| あなたの立場 | まずやること | 記事の該当箇所 |
| --- | --- | --- |
| 名刺やはがきに名前が載ったかもしれない人 | ラクスルや配送業者を名乗る連絡のリンク・電話番号を使わない | 「載っているかもしれない人へ」 |
| ラクスルで印刷を頼んだことがある人・会社 | 同社の続報で自分の注文が対象か確認する | 「入稿した側へ」 |
| 会社で宛名リストや名刺データを入稿している担当者 | 何人分を預けているか把握し、社内の個人情報担当に共有する | 「入稿した側へ」「入稿前に数えるスクリプト」 |
| エンジニア | 自社の保管システムの認証情報を見直す | 「自社のシステムに引きつけて考える」 |

## 何が起きたか

ラクスル株式会社の発表を時系列にすると、次のとおりです。

| 日時 | 公表されている内容 |
| --- | --- |
| 2026/11/08 0:20ごろ | 「データ入稿の処理に関わるシステム」への不正アクセスが発覚 |
| 2026/11/08 | 不正に使われた認証情報を無効化し、不正アクセスに使われたアカウントを停止。入稿を伴う一部サービスを停止 |
| 2026/11/09 7:00 | 順次再開。「ラクスル パッケージ」「ラクスル Adobe Express連携」、デザイン制作依頼サービス、カタログサイトは停止を継続 |
| 2026/11/09 | 公表。個人情報保護委員会へは報告予定 |

いつから漏れていた可能性があるのか（対象期間の始まり）は、まだ分かっていません。

手口に関わる記述は、発表の中で次の1文だけです。

> 当社システムの認証情報が不正に取得され、当社が保管するデータの一部に外部からアクセスできる状態にあったことを確認しています。

ここでの「認証情報」は、システムに入るための鍵にあたるものです。利用者のログインID・パスワードは漏えいしていないと発表されているので、利用者のパスワードとは別のものと読めます。
それが社員のアカウントなのか、システム同士をつなぐためのキーのようなものなのか、どう取得されたのかは公表されていません。この記事でも決めつけません。

## 影響範囲：「注文していない人」が含まれ得る

| 項目 | 公表内容 |
| --- | --- |
| 対象件数 | 集計中 |
| 対象データ | 入稿された印刷データ、請求書、Web郵便などのデータ |
| 記載情報 | 氏名、会社名、住所、電話番号、メールアドレスなど |
| 対象期間 | 調査中 〜 2026年11月8日 |
| 漏えいしていないことを確認したもの | クレジットカード情報、ログインID、パスワード |
| 二次被害 | 現時点で確認されていない |

発表には次の一文があります。

> 印刷データには、ご注文いただいたお客様の情報だけでなく、名刺やはがきなど、印刷物に記載された方の情報が含まれている場合があります。

会員情報の漏えいなら、影響を受けるのはそのサービスに登録した人です。
印刷データは違います。名刺なら社員本人、年賀状やDMの宛名面なら送り先が載ります。ラクスルを使ったことがない人も、対象に入り得ます。

自分は、ここが本件で一番考えておくべき点だと見ています。
会員ではない人には、サービスから直接の連絡が届きにくいと考えられるからです。どう通知するかは、まだ公表されていません。

## 会社の対応

公表されている対応は次のとおりです。

- 不正に使われた認証情報の無効化と、不正アクセスに使われたアカウントの停止
- 関係するサービスの一時停止と、安全確認後の順次再開
- 原因と影響範囲の調査、Webサイトでの続報の公表
- 個人情報保護委員会（個人情報の扱いを監督する国の機関）への報告（予定）
- 同社や関係事業者を装った不審なメール・SMS・電話への注意喚起

発覚から1日あまりで、停止中のサービス名まで挙げて公表しているので、利用者は自分の注文への影響を判断しやすくなっています。

## 載っているかもしれない人へ

自分の名刺や宛名が、誰の手でどこで印刷されたかは、本人にはまず分かりません。だから「自分が対象か」を調べるより、次の2つを習慣にするほうが確実です。

- ラクスルや配送業者、取引先を名乗るメール・SMSが来ても、本文のリンクや電話番号は使わない。確かめたいときは、公式サイトを自分で検索するかブックマークから開く。
- 「返金」「再発送」「本人確認」などを理由に、パスワードやカード番号を入力させる連絡には応じない。同社は、利用者自身の手続きによらずメールやSMSでパスワードやカード番号の入力を求めることはない、としています。

発表上、カード情報とパスワードは漏えいしていないとされているので、この件だけを理由にカードを止める必要はないと読めます。不安な場合は、同社の問い合わせフォーム（「個人情報保護相談窓口」を選択）から確認できます。

## 入稿した側へ

なぜ利用者側の話をするのか？　委託先の内部は外から変えられませんが、何を預けるかは入稿する側が決められるからです。

- **自分の入稿データが対象か確認する。** 対象期間の始まりは調査中なので、最近の注文に限らず確認しておくのが安全です。
- **会社として入稿している場合は、社内の個人情報担当（法務・総務など）に早めに共有する。** 顧客名簿を印刷会社に渡すことは、個人情報保護法でいう個人データの取扱いの「委託」にあたり得ます。その場合、漏えい時の個人情報保護委員会への報告や本人への通知を、委託元の会社側が求められることがあります（同法第26条。委託先が委託元に通知した場合、委託先の報告義務が免除される仕組みです）。自社が当てはまるかは個別の事情によるので、同委員会の[漏えい等の対応ページ](https://www.ppc.go.jp/personalinfo/legal/leakAction/)とラクスルからの連絡を確認してください。個人として年賀状を頼んだ場合は、通常この義務の対象ではありません。
- **保管期間と削除の手段を確認する。** 印刷が終わったデータがいつまで保管され、利用者が削除できるかを、規約や問い合わせで確認します。印刷・発送・DM代行のどれにも当てはまる話です。
- **入稿するデータを絞る。** 宛名リストに不要な列（生年月日、購入履歴など）が入っていないかを見ます。

## 入稿前に数えるスクリプト

ここからはエンジニア向けです。プログラムを使わない場合は、宛名リストの CSV を表計算ソフトで開いて行数を見るだけでも、何人分を預けるかは分かります。

宛名リストや名刺データを入稿するとき、そのファイルに何人分の情報が入っているかを把握している人は多くないと思います。
そこで、フォルダ内の PDF・テキスト・CSV から、メールアドレス・電話番号・郵便番号らしき文字列の**出現回数だけ**を数えるスクリプトを書きました。値もファイル名も出さず、通し番号で示します。ファイル名自体に個人名が入ることがあるためです。

```python:pii_scan.py
#!/usr/bin/env python3
"""入稿前フォルダの PDF/テキスト/CSV から、個人情報らしき文字列の「出現回数」だけを数える。
値そのものは表示しない。読めなかったファイルは stderr に出す。"""
import re, subprocess, sys, unicodedata
from pathlib import Path

PATTERNS = {
    "email": re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+"),
    "phone": re.compile(r"(?<![\d-])0\d{1,4}-\d{1,4}-\d{3,4}(?![\d-])"),
    "postal": re.compile(r"(?<![\d-])\d{3}-\d{4}(?![\d-])"),
}
TEXT_EXT = {".txt", ".csv", ".tsv"}

def read_text(p: Path) -> str | None:
    if p.suffix.lower() == ".pdf":
        r = subprocess.run(["pdftotext", "-q", "-enc", "UTF-8", str(p), "-"],
                           capture_output=True, encoding="utf-8", errors="replace")
        return r.stdout if r.returncode == 0 else None
    if p.suffix.lower() in TEXT_EXT:
        raw = p.read_bytes()
        encs = ("utf-16",) if raw[:2] in (b"\xff\xfe", b"\xfe\xff") else ("utf-8-sig", "cp932")
        for enc in encs:
            try:
                return raw.decode(enc)
            except UnicodeDecodeError:
                continue
        return None
    return None

def normalize(t: str) -> str:
    t = unicodedata.normalize("NFKC", t)               # 全角数字・＠・－ を半角に
    return re.sub(r"(?<=\d)[‐‑–—―ー−](?=\d)", "-", t)  # 数字の間のハイフン類をそろえる

root = Path(sys.argv[1] if len(sys.argv) > 1 else ".")
for i, p in enumerate(sorted(x for x in root.rglob("*") if x.is_file()), 1):
    t = read_text(p)
    if t is None:
        print(f"[skip] #{i} {p.suffix or '(拡張子なし)'}: 対象外か読み取り失敗", file=sys.stderr)
        continue
    if not t.strip():
        print(f"[empty] #{i}: テキストなし（画像やアウトライン化の可能性）", file=sys.stderr)
        continue
    t = normalize(t)
    counts = {k: len(v.findall(t)) for k, v in PATTERNS.items()}
    if any(counts.values()):
        print(f"#{i}\t" + "\t".join(f"{k}={n}" for k, n in counts.items()))
```

PDF の読み取りには poppler-utils の `pdftotext` を使います（Ubuntu なら `sudo apt install poppler-utils`）。Python 3.10 以上で、`python3 pii_scan.py 入稿前のフォルダ` のように実行します。

架空の名前・住所だけで作ったダミーデータ10ファイルで動かした結果です。

```text
$ python3 pii_scan.py demo
[skip] #1 .pdf: 対象外か読み取り失敗
[empty] #6: テキストなし（画像やアウトライン化の可能性）
[skip] #7 .png: 対象外か読み取り失敗
#3	email=0	phone=0	postal=1
#4	email=0	phone=1	postal=0
#5	email=1	phone=1	postal=0
#8	email=1	phone=1	postal=0
#9	email=1	phone=1	postal=0
#10	email=0	phone=2	postal=2
```

| # | ダミーデータ | 結果 |
| --- | --- | --- |
| 1 | 途中で切れた壊れたPDF | 読み取り失敗として報告 |
| 2 | 連絡先のないチラシ | 何も出ない（正しい） |
| 3 | Shift_JIS（CP932）の宛名CSV | 郵便番号1件 |
| 4 | UTF-16 の宛名CSV | 電話1件 |
| 5 | 名刺（テキスト） | メール・電話1件ずつ |
| 6 | 文字を画像にした名刺のPDF | テキストなしとして報告 |
| 7 | 文字を画像にした名刺のPNG | 対象外として報告 |
| 8 | 名刺（テキストから作ったPDF） | メール・電話1件ずつ |
| 9 | 全角で書いた名刺（`０３－…`、`＠`） | メール・電話1件ずつ |
| 10 | UTF-8 の宛名CSV（2人分） | 電話2件・郵便番号2件 |

最初の版では郵便番号の正規表現が電話番号 `03-1111-2222` の後ろ半分にも一致し、2件のはずが4件と出ました。前後に数字やハイフンが続く場合を除外して直しています。

### このスクリプトの限界

- **画像とアウトライン化された文字は数えられません。** 印刷入稿では文字を図形に変換（アウトライン化）したPDFや、AI・PSD形式がよく使われます。その場合は `[empty]` か `[skip]` になり、中身は数えられません。OCR（画像から文字を読む処理）を足せば拾えるはずですが、今回は試していません。
- **Excel（xlsx）や Word は対象外です。** CSV に書き出してから使ってください。
- **数えているのは人数ではなく出現回数です。** 名刺の TEL と FAX は電話2件になり、品番の `123-4567` は郵便番号と数えられます。多くも少なくも外れ得る目安です。氏名と住所は誤検出が多すぎるので数えていません。
- `(03)1234-5678` や `+81-3-…`、ハイフンなしの番号は拾いません。
- 試したのは自分で作った10ファイルだけで、実際の入稿データでの精度は測っていません。

正確に数えるための道具ではありません。入稿前に「このファイル、思ったより多くの人の情報が入っている」と気づくための道具です。

## 自社のシステムに引きつけて考える

本件の起点は「認証情報の不正取得」とされていますが、種類も取得方法も公表されていません。ここからは本件の原因の話ではなく、一般論としての自分の考えです。

外部からファイルを受け取って保管するシステムでは、保管場所を読み書きする権限を、何かしらの形で持たせることになります。それが長く使える固定のキーか、短時間で切れるトークンかで、取れる対策が変わります。見直すなら次の4点から始めます。

- 保管場所を読める認証情報が、どこに何本あるか（人のアカウント、CI、連携サービスのキーを分けて数える）
- 長期の固定キーを、短時間で切れるトークンや読み取り範囲を絞った権限に置き換えられないか
- 人のアカウントに多要素認証がかかっているか
- 保管場所への読み取りが監査ログに残っているか（クラウドによっては、データの読み取りログは既定で無効です）

## おわりに

本件は、件数も原因もまだ分かっていない段階です。続報で事実が変われば、この整理も更新します。
現時点で持ち帰れることは3つです。載っているかもしれない人は、届いた連絡のリンクを使わないこと。入稿した側は、何人分を預けたかを把握し、社内の担当に共有すること。システムを作る側は、保管場所を読める鍵を数えること。

預けたものの数は、預ける側も知っておく。

誤りや補足があれば、コメントで教えてもらえるとうれしいです。
